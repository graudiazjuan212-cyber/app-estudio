## Contrato de datos (nombres exactos, en español como el BRIEF)
```
Pack {
  schema: "estudio-pack/1"
  asignatura: { id: Id, nombre: string(1..80) }
  capitulo: { id: Id, numero: int ≥ 1, titulo: string(1..120) }
  version: int ≥ 1
  generado: "YYYY-MM-DD" (fecha real válida)
  bloques: Block[]   (1..60)
}
Block { id: Id, titulo: string(1..120), peso: 1|3|5, requiere: Id[] (default []), items: Item[] (1..200) }
Id = /^[a-z0-9][a-z0-9_-]*$/, 1..80 caracteres
```
Todo objeto es **estricto** (`z.strictObject`): un campo desconocido es un error (suele ser una errata), con mensaje que nombre el campo.

Campos comunes de todo ítem: `id: Id`, `tipo`, `etiquetas?: string[]` (≤ 10, cada una 1..40), `fuente?: string(≤ 200)`, `relaciona?: boolean`, `explicacion?: string(≤ 4000)` (Markdown+LaTeX; en `info` no aplica). Textos en general: no vacíos tras `trim()`, ≤ 4000 caracteres salvo indicación.

Tipos (unión discriminada por `tipo`):
| tipo | campos propios | reglas |
|---|---|---|
| `info` | `titulo` (1..120), `cuerpo` (1..8000) | no evalúa; sin `explicacion`/`relaciona` |
| `flashcard` | `anverso`, `reverso` | |
| `test` | `enunciado`, `opciones: {texto, correcta: boolean, feedback?}[]` | 3–5 opciones, **exactamente 1** correcta, textos de opción distintos (comparados normalizando espacios y mayúsculas) |
| `multi` | `enunciado`, `opciones` igual | 3–6 opciones, ≥ 1 correcta y ≥ 1 incorrecta, textos distintos |
| `vf` | `enunciado`, `correcta: boolean`, `feedback?` | |
| `ordenar` | `enunciado`, `pasos: string[]` | 3–8 pasos en el **orden correcto**; textos distintos |
| `emparejar` | `enunciado`, `pares: {izquierda, derecha}[]` | 3–6 pares; sin textos repetidos dentro de cada lado |
| `huecos` | `enunciado` (texto con marcadores `{{1}}`, `{{2}}`…), `huecos: {n: int, opciones: {texto, correcta, feedback?}[]}[]` | marcadores numerados desde 1 sin saltos, cada uno con su hueco y viceversa; 1–6 huecos; cada hueco 2–5 opciones con **exactamente 1** correcta y textos distintos; cada marcador aparece una sola vez |
| `error` | `enunciado`, `pasos: {texto, incorrecto: boolean}[]`, `correccion?` | 3–8 pasos, **exactamente 1** `incorrecto: true` |

Reglas de paquete (además del esquema), en `validate.ts`:
1. `id` de bloque únicos en el paquete; `id` de ítem únicos en todo el paquete y distintos de los ids de bloque, capítulo y asignatura.
2. `requiere`: cada id existe como bloque **del mismo paquete**; sin autoreferencia; sin ciclos (detectar con DFS; el mensaje nombra el ciclo `a → b → a`). *(En v1 los `requiere` entre capítulos no se admiten: si el id no está en el paquete es error con mensaje claro.)*
3. Si `relaciona: true`, el ítem debe ser evaluable (no `info`).
4. Cada texto con LaTeX (`$…$`, `$$…$$`) se comprueba con KaTeX; el error nombra la ruta y el fragmento. Implementar el extractor de fórmulas en `src/domain/pack/latex.ts` (función pura `extractMath(text): {kind: 'inline'|'display', source: string}[]`) que **ignora** el contenido de bloques de código (``` y `…`) y `\$` escapado, y que trata `$` suelto sin cerrar como error «`$` sin cerrar» (a menos que esté escapado). Un precio como «5 \$» se escribe con `\$`.
5. Un bloque con solo ítems `info` es válido pero genera **aviso** (no error) «bloque sin preguntas evaluables».

## API
```ts
type PackError = { path: string; message: string };       // path tipo "bloques[2].items[5].opciones[1].texto"
type PackWarning = { path: string; message: string };
type ValidationResult =
  | { ok: true; pack: Pack; warnings: PackWarning[] }
  | { ok: false; errors: PackError[] };                    // todos los errores a la vez, máx. 50, ordenados por aparición
function validatePack(input: unknown): ValidationResult;
function validatePackText(text: string): ValidationResult; // JSON.parse con error legible: «El archivo no es un JSON válido: …» (con línea/columna si el motor la da). Quitar BOM inicial.
function formatErrors(errors: PackError[]): string;        // texto multilínea para mostrar al usuario
```
**Mensajes en español de España**, comprensibles para una persona no programadora, que digan *qué* y *dónde*, p. ej.: `Bloque 3 «Norma», pregunta 5 (id mat1-c02-b03-i05): el test debe tener exactamente 1 opción correcta y tiene 2.` Para ello el validador resuelve la ruta a una descripción con título de bloque y número de pregunta cuando es posible, **y conserva el `path` técnico**. Traducir (con `z.config`/`error maps` o post-procesado) los mensajes de zod para tipos incorrectos, campos que faltan («Falta el campo `enunciado`»), valores no permitidos («`peso` debe ser 1, 3 o 5») y campos desconocidos («Campo desconocido `enunciadoo`; ¿querías decir `enunciado`?» — sugerir el campo válido más parecido por distancia de edición ≤ 2).

`diffPack(previous, next)`: devuelve
```ts
type PackDiff = {
  newItems: string[];            // ids que no estaban
  keptItems: string[];           // mismo id y mismo tipo
  archivedItems: string[];       // estaban en previous y ya no en next
  typeChanged: { id: string; from: ItemType; to: ItemType }[]; // mismo id, distinto tipo (→ generación nueva, ADR-002)
  movedItems: { id: string; fromBlock: string; toBlock: string }[];
  removedBlocks: string[]; newBlocks: string[];
  versionRelation: 'first' | 'newer' | 'same' | 'older';
}
```
- `previous === null` → todo es `newItems`, `versionRelation: 'first'`.
- Si `previous.capitulo.id !== next.capitulo.id` o las asignaturas difieren → lanzar `Error` (el llamador decide; documentarlo). Las listas van ordenadas por orden de aparición en el paquete (determinista).
- Un `info` cuenta como ítem como los demás.

## Tests obligatorios
- Cada fixture válido pasa y devuelve el número esperado de bloques/ítems (valores fijos escritos en el test).
- Cada fixture inválido produce el error esperado con su `path`.
- Una regla = al menos un test positivo y uno negativo (límites: 3 y 5 opciones en `test`; 2 y 3 pasos en `ordenar`; peso 1/3/5/2/0).
- `validatePack` devuelve **todos** los errores a la vez (un paquete con 3 fallos distintos → ≥ 3 errores) y corta en 50.
- `validatePackText`: BOM inicial, JSON vacío, JSON con coma final, JSON que no es objeto (`[]`, `null`, `"x"`).
- `extractMath`: `$a$`, `$$a$$`, `\$5`, código con `$` dentro (ignorado), `$` sin cerrar (error), varias fórmulas por texto, `$$` multilínea.
- Distancia de edición: `enunciadoo` → sugiere `enunciado`; `zzz` → sin sugerencia.
- `diffPack`: ítem igual, eliminado, reaparecido (previous sin él, next con él → nuevo), cambio de tipo, movido de bloque, bloque nuevo/eliminado, `previous === null`, versiones iguales/menores, capítulos distintos → lanza.
- Round-trip: `docs/estudio-pack-1.schema.json` coincide con el exportado, y los 3 fixtures válidos validan contra ese JSON Schema usando el propio zod (`z.fromJSONSchema` si existe en la versión instalada; si no existe, omitir ese test y decirlo en la respuesta final).
- Propiedad simple (sin librería nueva): generador pseudoaleatorio con semilla fija que produce 200 paquetes válidos variados y todos validan; mutar un campo obligatorio al azar en cada uno siempre produce error.
