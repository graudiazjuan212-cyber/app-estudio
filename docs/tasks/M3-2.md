# M3-2 · Copias de seguridad, restauración con snapshots y persistencia

## 1. Contexto y por qué importa
Android o el navegador pueden borrar el almacenamiento; la copia es la red de seguridad de Juan (ADR-012). Un restaurar equivocado o interrumpido **no puede** destruir su estado actual. Esfuerzo Codex: **high**. Depende de M3-1. Codex no ejecuta npm ni hace commits.

## 2. Estado verificado
Debe existir `src/data/` de M3-1 (`schema.ts`, `db.ts`, `open.ts`, `catalog.ts`, `importPack.ts`, `attempts.ts`, `cache.ts`) con la tabla `snapshots` y `meta`. Claude lo verifica antes de lanzar esta tarea.

## 3. Lo que quiero

### Archivos (`src/data/`, ≤ 300 líneas cada uno)
`backupSchema.ts` (zod + tipos), `backupMigrations.ts` (funciones puras), `backup.ts` (`exportBackup`, `restoreBackup`, `undoRestore`, `listSnapshots`), `storage.ts` (persistencia/almacenamiento), `reminder.ts` (recordatorio de copia). Constantes en `dataConfig`: `backupSchema: 'estudio-backup/1'`, `backupReminderDays: 7`.

### Formato `estudio-backup/1` (`backupSchema.ts`)
```ts
{ schema: 'estudio-backup/1', createdAt: ISO UTC, dbVersion: int ≥ 1, schedulerVersion: int ≥ 1,
  data: { subjects, chapters, blocks, items, packs, attempts, sessions, settings } }   // arrays de filas, tipadas con zod estricto
```
**No incluye** `itemState`, `blockState` (cachés, se recalculan), **ni** `snapshots`, **ni** `meta`. Incluye **todas las versiones** de cada paquete (`packs`) y **todos** los intentos. Todos los objetos son `strictObject`. Cada fila de `attempts` se valida con las mismas reglas que `validateAttempt` (un intento inválido ⇒ la copia **entera** se rechaza). Referencias: cada intento debe apuntar a un `itemId` existente en `items`, cada ítem a un bloque existente, cada bloque a un capítulo existente (integridad referencial comprobada; si no ⇒ rechazo con mensaje).

### Exportar
`exportBackup(db, ctx: { now: string }): Promise<{ json: string; fileName: string; counts: Record<string, number> }>` — una **transacción de lectura** (instantánea coherente). `fileName = backup_estudio_<AAAA-MM-DD>.json` con la fecha UTC de `ctx.now` (los nombres `backup_*.json` ya están en `.gitignore`). No escribe en la BD (el registro de «última copia» lo hace `markBackupDone(db, now)` cuando la UI confirma que se compartió/descargó). `json` se genera con `JSON.stringify` determinista (claves en orden fijo, filas ordenadas por su clave primaria) para que dos exportaciones del mismo estado sean **idénticas byte a byte**.

### Restaurar
```ts
export type RestoreResult =
  | { status: 'restored'; counts: Record<string, number>; snapshotId: number }
  | { status: 'rejected'; message: string };
export async function restoreBackup(db: StudyDb, text: string, ctx: { now: string; tz: string }, migrations?: BackupMigration[]): Promise<RestoreResult>
```
1. **Antes de tocar nada**: normalizar (JSON puro, límite de profundidad como en M1), parsear con zod, comprobar integridad referencial, calcular **en memoria** las cachés con `rebuildFromAttempts` sobre los datos del archivo. Cualquier fallo ⇒ `rejected` con mensaje en español; **la BD no se toca**.
2. Versiones: `schema` distinto de `estudio-backup/1` ⇒ rechazo «No es una copia de esta app». `dbVersion` **mayor** que la actual ⇒ rechazo «Actualiza la app antes de restaurar esta copia» (sin tocar nada). `dbVersion` **menor** ⇒ se migra en memoria aplicando en orden las `BackupMigration` (`{ from: number; to: number; migrate(data: unknown): unknown }`, funciones puras) y se revalida; si falta algún eslabón o la migración lanza ⇒ rechazo. La lista por defecto está vacía (solo hay v1); el parámetro `migrations` permite probar la cadena.
3. **Una sola transacción** `rw` sobre todas las tablas de datos + cachés + `snapshots` + `meta`: (a) exporta el estado **actual** como snapshot (`reason: 'before-restore'`, `json` = el mismo formato de copia) y lo guarda en `snapshots`; (b) se conservan solo los `dataConfig.snapshotKeep` (3) snapshots más recientes; (c) vacía las tablas de datos y cachés (**nunca** `snapshots`); (d) escribe los datos del archivo y las cachés calculadas; (e) actualiza `meta`. Si algo falla (cuota, aborto, error) ⇒ la transacción se deshace entera y el estado previo **queda intacto**; la promesa devuelve `rejected` (no lanza) con mensaje claro.
4. `undoRestore(db, ctx): Promise<RestoreResult>` — restaura el snapshot más reciente por **el mismo camino** (`restoreBackup` con su `json`), de modo que guarda a su vez un snapshot del estado actual (reversible otra vez). Sin snapshots ⇒ `rejected` («No hay nada que deshacer»). `listSnapshots(db): Promise<{ id: number; createdAt: string; reason: string; counts: Record<string, number> }[]>` (más reciente primero; sin devolver el JSON).
5. No muta el texto de entrada.

### Persistencia y espacio (`storage.ts`) — ADR-018
Funciones que **reciben** el `StorageManager` (o un objeto compatible) y no tocan `navigator` global:
- `requestPersistence(storage: StorageLike | undefined): Promise<'granted' | 'denied' | 'unsupported'>` (comprueba que `persist` existe; captura excepciones ⇒ `'denied'`; ya persistente ⇒ `'granted'` sin volver a pedir).
- `storageStatus(storage): Promise<{ persisted: boolean | null; usageBytes: number | null; quotaBytes: number | null }>` (`null` si no hay soporte o falla).
- `canShareFile(nav: { canShare?: (d: ShareData) => boolean; share?: unknown } | undefined, file: File): boolean`.

### Recordatorio (`reminder.ts`)
`markBackupDone(db, now): Promise<void>` (escribe `meta.lastBackupAt`), `getLastBackup(db): Promise<string | null>`, `backupReminderDue(lastBackupAt: string | null, now: string): boolean` — pura: `true` si nunca hubo copia **y existe al menos un intento** (parámetro `hasAttempts`) o han pasado **≥ 7 días** (comparando instantes: 7 × 24 h exactas); `false` en otro caso (`backupReminderDue(lastBackupAt, now, hasAttempts)`).

## 4. Lo que NO hay que hacer
No UI. No tocar `src/domain/`. No incluir `snapshots`, `meta` ni cachés en la copia. No `any`/`eslint-disable`/`@ts-ignore`. No `Date.now()`. No `navigator` global. No dependencias nuevas. No ejecutar npm ni hacer commits.

## 5. Verificación exigida (`fake-indexeddb`, BD con nombre único por test)
Estado de partida común: importar `mat-ejemplo-c01` y `ioe-ejemplo-c01` + 12 intentos fijos de 3 ítems en 4 días (helpers de M3-1).
1. `exportBackup` ⇒ JSON válido contra el esquema; `counts` correctos (valores escritos a mano: 2 asignaturas, 2 capítulos, 5 bloques, 24 ítems, 2 paquetes, 12 intentos); **no** contiene las claves `itemState`, `blockState`, `snapshots`, `meta`; dos exportaciones seguidas **idénticas byte a byte**; `fileName === 'backup_estudio_2026-11-24.json'` para `now = 2026-11-24T10:00:00Z`.
2. **Ida y vuelta**: exportar ⇒ BD **nueva** vacía ⇒ `restoreBackup` ⇒ `restored`; volcado de todas las tablas de datos **idéntico** al original y cachés (`itemState`/`blockState`) iguales a los del original.
3. Restaurar sobre una BD con datos distintos ⇒ el snapshot guardado contiene exactamente el estado previo (restaurarlo da el estado previo idéntico); `listSnapshots` devuelve 1.
4. **Deshacer**: restaurar A (sobre B) y `undoRestore` ⇒ vuelve a B idéntico; `undoRestore` otra vez ⇒ vuelve a A idéntico; repetir 4 veces seguidas: nunca quedan más de 3 snapshots y el estado coincide en cada paso.
5. `snapshots` **nunca** aparece en una copia y restaurar **no** borra los snapshots existentes (salvo la poda a 3).
6. Archivo corrupto (JSON truncado, `schema` incorrecto, campo extra, intento inválido, ítem de un intento inexistente, bloque sin capítulo, profundidad excesiva, vacío) ⇒ `rejected` y **volcado completo de la BD idéntico antes/después** (incluidos `snapshots`).
7. `dbVersion` futuro ⇒ `rejected` «Actualiza la app antes de restaurar…», BD intacta. `dbVersion` antiguo con una migración de prueba `{from:0,to:1}` que renombra un campo ⇒ restaura y los datos reflejan la migración; migración que lanza o hueco en la cadena ⇒ `rejected`, BD intacta.
8. **Fallo durante la escritura** (`vi.spyOn(db.attempts, 'bulkAdd')` o `db.items` lanza; y otra prueba que lanza en `snapshots.add`) ⇒ `rejected` y volcado previo idéntico (el estado previo íntegro; sin snapshot huérfano).
9. Cuota simulada: `vi.spyOn` que lanza `DOMException('QuotaExceededError')` ⇒ mismo resultado que 8.
10. `restoreBackup` calcula las cachés del archivo: con una copia hecha con **otro** `tz`/`now`, los `studyDay` de los intentos **no se reinterpretan** (se conservan tal cual).
11. Rendimiento: exportar y restaurar 20 000 intentos sintéticos < 5 s en total (tolerante).
12. `requestPersistence`: con fakes — `persist()` ⇒ `true` ⇒ `'granted'`; ⇒ `false` ⇒ `'denied'`; lanza ⇒ `'denied'`; sin `persist` o `undefined` ⇒ `'unsupported'`; ya `persisted()` ⇒ `'granted'` sin llamar a `persist`. `storageStatus`: con `estimate` válido, sin él, y con `estimate` que lanza. `canShareFile`: con `canShare` verdadero/falso/ausente y sin `share`.
13. `backupReminderDue`: nunca hubo copia y sin intentos ⇒ `false`; nunca y con intentos ⇒ `true`; última copia hace 6 d 23 h ⇒ `false`; hace exactamente 7 d ⇒ `true`; hace 8 d ⇒ `true`; instantes inválidos ⇒ `true` (fallar hacia recordar). `markBackupDone` ⇒ `getLastBackup` devuelve el instante.
